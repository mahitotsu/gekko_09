# 計画: docs/inventory-design.md（在庫予約の同時実行対策 設計書）

## Context
`src/inventory.js` の `Inventory.reserve` は `await store.get` → 判定 → `await store.set` の read-modify-write になっている。2 つの await の間に別の reserve が割り込めるため、同じ SKU に同時に注文が来ると、両方が古い在庫を読んで両方とも true を返す（lost update が起き、在庫以上に予約が通る）。`release` にも同じ競合があり、reserve と release が重なると加算/減算のどちらかが消える。
store のインターフェース `{ get(sku), set(sku, n) }` は変えられない（CAS もトランザクションもない）。成果物は設計書 1 本だけで、コードは変更しない。

根拠となる資料: `src/inventory.js`（L8-18 が競合箇所、L22-35 の `memoryStore` は get/set それぞれ 5ms の遅延があり再現に使える）。`test/basic.test.js` に inventory のテストはない。`src/cart.js` は在庫に触れないので対象外。

## 解釈の決定
- **前提とする実行環境: Node の単一プロセス**。get/set だけでは、複数のプロセスが同じ store に書く場合の排他は原理的に作れない（CAS がないため）。これは設計書に「前提と限界」として明記し、複数プロセスに広げる場合の選択肢（SKU ごとに担当プロセスを 1 つに決めてルーティングする／store の拡張が必要）を節として書く。ユーザーの「インターフェースを変えない」という制約はこの範囲で守る。
- **採用する方式: Inventory 内に SKU 単位の非同期ロック（Promise チェーンのキュー）を置く**。reserve と release はどちらも同じロックの下で get→set を行う。SKU が違えば並行に動き、同じ SKU だけ直列になる。
- 不採用の案とその理由も短く書く: グローバルな単一ロック（無関係な SKU まで直列になる）、プロセス内に在庫をキャッシュして store を書き戻す方式（store と食い違う、再起動時に失われる）、set の後で get して確かめる方式（検証と set の間にも割り込みが入るので防げない）。

## 設計書の構成（docs/inventory-design.md）
1. **背景と問題** — 競合のタイムライン例（在庫 1、reserve(1) が 2 つ → どちらも stock=1 を読む → どちらも true）。release も同じ問題を持つ。
2. **制約と前提** — get/set は変えない、呼び出し側の API（`reserve`/`release` のシグネチャと戻り値）も変えない、単一プロセスを前提とする。
3. **方式** — SKU ごとのロック。`Map<sku, Promise>` の末尾につなぐ方式、`finally` で必ず解放、キューが空になったら Map から消す（メモリリーク対策）。擬似コードで示す（実装はしない）。
4. **エラー時の振る舞い** — get/set が reject した場合はロックを解放したうえで呼び出し元へ例外を伝える。set の失敗で結果が不明になる問題（書けたかどうか分からない）を明記する。リトライはしない方針とする。
5. **漏れやすい観点**
   - release も同じロックを通す必要がある。
   - qty の検証（0 以下・整数でない値）：今回の対象外として記録するにとどめる。
   - ロック待ちの上限：store が止まると後続がずっと待つ。タイムアウトの導入は今後の課題とし、`config.js` の `DEFAULT_TIMEOUT_MS` を流用できる可能性に触れる。
   - 公平性：Promise チェーンは到着順（FIFO）。
   - 性能：同じ SKU の処理は 1 件あたり get+set の 2 往復分だけ直列になる。人気商品では待ちが増える。
6. **限界と複数プロセスへの拡張** — 複数プロセスでは防げないこと。対策の候補: SKU ごとに担当プロセスを決めるルーティング（インターフェースは変えずに済む）、または将来 store に原子的な操作（`decrementIfAtLeast` や CAS）を追加すること。
7. **検証方法（テスト計画）** — `memoryStore({ a: 1 })` を使って `Promise.all` で reserve(a,1) を 10 本流し、true が 1 本だけで最終在庫が 0 になること。reserve と release を混ぜても在庫の合計が保たれること。SKU が違う場合は並行に動く（所要時間が直列にならない）こと。get/set が失敗した後も次の呼び出しが詰まらないこと。`node --test` で実行する。
