# 計画: docs/design.md（請求書発行システム 設計書）の作成

## Context
docs/requirements.md（要件）をもとに、実装の前に設計書 docs/design.md を書く。実装はしない（src/ には何も書かない）。
書く内容は、モジュールの構成、データの流れ、計算の手順（請求期間・単価・数量割引・送料・返品・消費税・繰越）、エラー処理。

## 資料の優先順位（食い違うときに採る方）
1. 連携仕様書 第4版（要件の冒頭で「正とする」とされている）
2. 請求業務規程（2026-09-01 改定）
3. 議事録は新しい回が優先（第4回 > 第3回 > 第2回 > 第1回）。requirements.md は 1〜3 の要約として使う。
- 食い違いの例と採る方: 第3回 決定4「注文がない顧客には発行しない」→ 第4回 決定4 を採る／第1回の 5,000円・特約店 5%・明細ごとの切り捨て → 第2回を採る／第2回の「10月の価格改定」と第4回の「9月から」→ 第4回（商品マスタの valid_from に従うので、設計としては日付を固定しない）／明細の並び順は第3版ではなく第4版 6.2 を採る。

## design.md の構成と各節の要点（根拠）
1. **概要と前提** — 目的・範囲（PDF は範囲外）、Node.js 24、外部パッケージなし、入口 src/cli.js（要件 1・2.1、連携 2章）。資料の優先順位（上記）。
2. **モジュール構成** — src/ 以下のファイルと責務、依存の向き（cli → 各モジュール、計算は入出力をしない純粋な関数）。
   - `cli.js` 引数の解析と終了コード／`args.js` 引数の検査／`csv.js` CSV の読み書き（クォートなし、LF、末尾改行）／`load.js` 6ファイルの読み込みと型変換／`validate.js` 不整合の検査（全行）／`period.js` 請求期間・日付／`pricing.js` 価格の解決・特約店・数量割引／`invoice.js` 顧客ごとの請求書と明細の組み立て（送料・返品・繰越）／`tax.js` 消費税と端数処理／`output.js` 列の順・並び順・書式／`errors.js` ArgError(1)・DataError(2)
3. **データの流れ** — 引数検査 → 6ファイル読み込み → 型変換 → 全行の不整合検査（ここまでに問題があれば何も書かずに終了）→ 索引作り（顧客・商品の価格履歴・注文番号→明細）→ 顧客ごとに期間を求め、注文・返品・入金・前回請求額を集める → 明細と金額 → 税 → 発行の判定 → 並べ替え → 出力ディレクトリ作成と2ファイルの書き込み。図はテキスト（矢印）で書く。
4. **内部のデータ構造** — Customer、PriceRow、OrderLine（行番号を保持：明細順に使う）、Return、Payment、Balance、計算後の Line（price 解決済み・金額）、Invoice。
5. **計算の手順**（各項で式・端数・根拠を書き、サンプルの数値で1つずつ例を示す）
   - 5.1 請求期間（規程4条）: 末＝対象月1日〜末日。d日締め＝前月 d+1 日〜対象月 d 日、1月は前年12月から。閉区間。日付は `YYYY-MM-DD` の文字列比較で扱い、Date のタイムゾーン問題を避ける。例: C002 20日締め 2026-09 → 2026-08-21〜2026-09-20。
   - 5.2 単価（規程5条、第4回 決定1）: 商品の行のうち valid_from ≤ 注文日で最大のもの。税率・商品名も同じ行。特約店は floor(単価×90/100)。
   - 5.3 数量割引（第3回 決定1）: 金額 = 単価×数量。数量 ≥100 なら 割引額 = floor(金額×5/100)、金額 − 割引額。例: 110×100=11000 → 10450。
   - 5.4 送料（第2回 決定2、第3回 決定2）: 注文ごとに商品の金額（割引後、8%も含む）の合計 ≥10000 なら無料、否なら A800/B1000/C1500。送料行は 10%、注文の最後の明細。返品で判定は変えない。
   - 5.5 返品（規程8条、第4回 決定2）: 返品日が期間内なら計上（顧客は元の注文の顧客、元の注文の期間は問わない）。金額 = −floor(元の金額×返品数量÷元の数量)（絶対値で切り捨ててから符号を付ける）。単価・税率・商品名は元の明細。例: 10450×30/100 → −3135。
   - 5.6 消費税（規程7条、第2回 決定3・4、第4回 決定5）: subtotal_10（商品+送料+返品）、subtotal_8（商品+返品）。税 = 符号×round(|subtotal|×税率/100)。端数処理は整数演算で（floor: ⌊n/100⌋、四捨五入: ⌊(n+50)/100⌋、切り上げ: ⌊(n+99)/100⌋、n=|subtotal|×税率）。浮動小数点を使わない理由も書く。空欄は切り捨て。
   - 5.7 繰越（規程9条、第4回 決定3・確認事項）: previous_balance = balances の対象月の前月の行（1月なら前年12月）、なければ 0、2か月以上前は使わない（例: C006 の 2026-07 は無視）。payment = 入金日が期間内の合計。carried_over = previous − payment（負もあり）。total = 小計+税、total_due = carried_over + total。
   - 5.8 発行の判定（第4回 決定4）: 期間内の確定注文・返品・入金がどれも0件で、previous_balance が 0 の顧客は出さない。例: C007（前回請求額と入金だけ）は出す。
   - 5.9 件数: order_count＝期間内の確定注文の注文番号の数、return_count＝返品番号の数。
6. **出力**（連携 4章・6章）— 列の順、invoices は顧客コード昇順、明細の並び順（請求書番号 → 日付 → 同日は注文（注文番号順、受注データの行順、送料は最後）→ 返品（返品番号順））。書式（整数、マイナスは `-`、LF、末尾改行、UTF-8 BOM なし）。0件なら見出しだけ。出力ディレクトリは作る、上書き。
7. **エラー処理** — 終了コード表。
   - 1: 引数不足・未知の引数・`--month` 形式（`YYYY-MM`、月 01〜12）・`--data` がディレクトリでない。
   - 2: 3.1 の各不整合（受注・返品・入金・前回請求額）。全行を調べ、見つかったものをすべて標準エラーに出してから終了（1件目で止めない）。メッセージに番号を含める。メッセージの書式例を示す。
   - 返品数量超過の判定は、同じ明細の返品を「返品日、同日は返品番号」の順に累計し、超えた時点の返品番号を示す。
   - 出力は全部の計算が終わってから書く（途中で失敗してもファイルを作らない）。
   - 仕様にない入力の誤り（ファイルがない、列が足りない、数値でない、日付の形式、closing_day・zone・rank・rounding・status・tax_rate の値が不正）も終了コード 2 とし、ファイル名と行番号を示す（設計で決めたことと明記）。
8. **設計で決めたこと（仕様に明記がない点）** — 上の判断を一覧にする: 返品の切り捨ては絶対値で／超過の累計順／発行判定の「前回の請求額がない」は金額 0 を含む／不正な値は終了コード 2／整数演算／日付は文字列で比較。
9. **確かめ方（テストの方針）** — node:test で単体（period, pricing, tax, 返品）と、サンプルデータ `docs/資料/data` に `--month 2026-09` を流して連携仕様書 7章の出力と一致することを確かめる。不整合のケース（各種）で終了コード 2 と出力なし、引数の誤りで 1。境界: 1月分、2月の28日締め、四捨五入の 0.5、税率ごとの合計がマイナス、数量 99/100、送料の判定 9999/10000。

## 漏れやすい観点（本文で必ず触れる）
- 返品の行も期間で選ぶ（注文の期間ではなく返品日）。取消注文の返品は不整合。
- 送料の判定は割引後・8%込み、返品で変えない。送料は返金しない。
- 返品の商品名・単価・税率は元の注文日の価格の行。
- 検査は期間外・取消の注文も含む全行。
- 前回請求額は前月のみ。
