# model-router v2 作業計画

## 目的

Claude Code / Agent SDK で使える汎用的なルーティングにする。Opus 5.5 単独と比べて、品質を保ったまま、コストとレイテンシを大幅に下げる。

## 前回（v1）の結果から引き継ぐこと

- 効果の大部分は、軽い依頼を Haiku に回したことによる。毎回送る固定費（システムプロンプトとツール定義）の単価が、モデルによって大きく違うため。
- Sonnet 単独だけで Opus 単独より 48% 安く、品質の差は見えなかった。ルーターは Sonnet 単独にも勝つ必要がある。
- タスクがモデル間で差の付かない難しさだったため、品質を評価できなかった。
- 評価は1ターンの会話だけだったため、キャッシュと会話の文脈の影響を測れていない。

## 方針

### 振り分けの基本（公式のガイドに基づく）

| 段階 | モデル | 使う場面 | 根拠 |
| --- | --- | --- | --- |
| 下 | Haiku 5.5 | 単純な作業、下調べ、サブエージェントのタスク | [model-config](https://code.claude.com/docs/en/model-config) の「haiku: simple tasks」、[choosing-a-model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model) の「sub-agent tasks」と「効率優先で始める」 |
| 標準 | Sonnet 5.5 | 日常のコーディング | 「sonnet: daily coding tasks」 |
| 上 | Opus 5.5 | 複雑な推論、計画 | 「opus: complex reasoning tasks」、`opusplan`（計画モードは Opus、実行は Sonnet） |

- effort は、作業の種類で決める（公式の目安）。low は小さな変更、medium は範囲が明確な実装、high は検証が大事な不具合修正。
- Haiku を積極的に使う。ただし、難しい依頼を Haiku に回すミスは重く数える。
- 振り分けの判断材料は3つ。
  1. ヒューリスティック（はっきりした場合だけ使う）
  2. Haiku による判定（迷う場合）
  3. 途中で上げる仕組み（テストの失敗やエラーの連続を見て、上位モデルへ）
- 判断の入力には、依頼文に加えて会話の状態を含める。現在のモデル、直前の失敗、計画モードかどうか、会話の大きさ、上位モデルのキャッシュが残っていそうか。

### 計画から実行まで1ターンで進む場合

ターンの開始時だけ判定すると、1ターンで最後まで進む作業では、振り分けが最初の1回きりになる。`turn.step` はリクエストごとに呼ばれるので、次の方法でターンの途中でも振り分ける。

- **既定の動作**:
  - **サブエージェントに任せる**: Haiku で動く調査用・テスト実行用のエージェントの種類を登録し（`$.agent.register`）、システムプロンプトで任せるよう促す（`prompt.compose`）。サブエージェントは専用の文脈で動くので、メインの会話のキャッシュと思考の連続性を壊さない。公式の「指揮役が作業を安いモデルに任せる」型にあたる。
  - **計画モードの切り替え**: 計画モードを抜けた（`ExitPlanMode` が呼ばれた）ら、それまでを Opus、それ以降を Sonnet にする（`opusplan` と同じ考え方）。
  - **失敗時に上げる**: 同じターンの中でテストの失敗やエラーが続いたら、Opus に上げる。
- **比較対象として測るもの**: 直前のステップが読み取りや検索ばかりなら、Haiku に下げる。
- ステップごとの判定はヒューリスティックだけで行い、LLM は呼ばない（レイテンシを増やさないため）。
- 行ったり来たりを防ぐため、一度切り替えたらしばらく維持する。
- 思考ブロックはモデルをまたぐと引き継がれないので、ターンの途中での切り替えが品質に響くかを実測する。

### Claude Code で使うときの制約

- プロンプトキャッシュはモデルごとに別。切り替え先のモデルでは書き直しになる。元のモデルに戻ったときは、そのキャッシュがまだ残っていれば（通常5分、設定によっては1時間）再利用できる。
- Haiku に下げること自体は、会話が大きくても安い。高くつくのは、キャッシュが切れた上位モデルに戻るとき。v1 の下げ止めの規則（会話が大きくなったら下げない）は見直す。
- Haiku 5.5 は、プロンプトが 100K トークンを超えると単価が5倍になる。
- 会話の途中で effort を変えても、Claude Code ではキャッシュは無効にならない（P1 で、Haiku・Sonnet・Opus について実測）。API の資料では、最上位の effort を変えるとメッセージのキャッシュが無効になるとされているが、mod から `turn.step` で変えた場合は該当しなかった。
- 思考ブロックは、モデルをまたぐと引き継がれない。
- mod から変えられるのはモデルと effort だけ。思考のオン・オフは変えられない。

### 再現性（この環境に依存しない測定）

インフラ側の待ち行列など、制御できない要因は対象外とする。

- **実行環境**: クリーンなコンテナで実行する。Claude Code と Agent SDK の版を固定し、設定用のディレクトリは空にする（`CLAUDE_CONFIG_DIR` などでホストの `~/.claude` から切り離す）。
- **認証**: `claude setup-token` で取得したトークンを、実行時の環境変数としてコンテナに渡す（変数名は `CLAUDE_CODE_OAUTH_TOKEN` の想定。P0 で確認する）。
  - Anthropic の API キーと AWS Bedrock は使わない。
  - トークンはリポジトリ、イメージ、結果のファイルに含めない。保存場所はリポジトリ直下の `.env`（`.gitignore` と `.dockerignore` に登録済み、権限 600 が必須）か、`EVAL_ENV_FILE` で指定したファイル。
  - サブスクリプションの利用上限がかかるので、並列の数と実行の順番は、上限に達しても続きから再開できる形で運用する。
- **主な指標は、環境に依存しにくいものにする**:
  - **トークン数**: モデル別の入力、キャッシュの読み、キャッシュの書き、出力の量。コストは、公開の価格表からスクリプトで計算する。SDK の `total_cost_usd` は概算なので補助の扱いにする。
  - **レイテンシ**: API の応答時間（`duration_api_ms`）とリクエストの回数を主にする。ローカルの処理を含む全体の時間は参考値にする。
- **環境の記録**: 実行ごとに、Claude Code・SDK・モデルの版、初期化の情報（ツール、MCP、スキル、プラグインの一覧）、1回目のリクエストの入力トークン数を記録し、結果と一緒に公開する。
- **キャッシュ**: 読み書きの量から計算し直して、キャッシュが冷えた状態と温まった状態のコストを分けて示せるようにする。
- **並列の数**: 固定して報告する。
- **言語**: 日本語での利用を前提に測る。タスク、台本、外部資料は日本語で作る。実行環境は `language: "japanese"`（Claude の応答言語の設定）、タイムゾーン Asia/Tokyo にする。

## 目標（通しの評価の前に確定させる）

案:

- **コスト**: Opus 単独の 50% 以下
- **レイテンシ**: 中央値が Opus 単独の 70% 以下
- **品質**: シナリオの受け入れテストの合格率と文書の採点が、Opus 単独より統計的に有意に下がらない
- **Sonnet 単独との比較**: 品質かコストのどちらかで、Sonnet 単独に勝つ
- **報告する値**: Haiku が担当した割合（ターン数とトークン数）

  - トークンなしの `--env-only` では、スキルは CLI 同梱の18個、MCP は0、`apiKeySource` は `none` だった。

- [x] 同じタスクを複数回実行し、合格率を集計できるようにする
  - `--reps N` で実行し、集計にタスクごとの合格率（k/n）の表を出す。

#### P0 で分かったこと（後の段階に影響するもの）

- サブスクリプションのトークンでは、Claude Code はキャッシュを1時間の TTL で書く。書き込みは入力単価の2倍になる。
- 別の実行のキャッシュが再利用される。同じモデルなら、比較対象や effort が違っても、1回目のリクエストが前の実行の書いた前置き（約 11.9K トークン）を読んだ。比較対象を交互に実行するので、冷えた状態と温まった状態のコストを分けて示す。
- `duration_api_ms` は複数ターンの会話では累計で返る（`duration_ms` はターンごと）。

#### 実測と公式の記載の照合（2026-10-10）

一致したもの:

- effort を変えてもキャッシュが残る: Claude Code の [prompt-caching](https://code.claude.com/docs/en/prompt-caching#changing-effort-level) に「Opus 5.5、Sonnet 5.5、Haiku 5.5 では、API キーか Claude のサブスクリプションなら、effort を変えてもキャッシュは残る」とある（API の資料の、メッセージ単位で effort を変える仕組みに当たる）。Bedrock などや、`CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` を設定した場合は当てはまらない。
- モデルを切り替えると、切り替え先で会話全体を書き直す: 同じページの「Switching models」。`opusplan` の計画モードの切り替えも、モデルの切り替えとして扱われる。
- キャッシュの TTL: サブスクリプションでは、メインの会話が1時間、サブエージェントやセッションのタイトルなどは5分（同じページの「Which TTL each request gets」）。契約プランの利用量を超えて追加の利用分に入ると、メインの会話も5分に下がる。
- システムプロンプトとツール定義の分だけが実行をまたいで共有される: 同じモデルで前置きが同じなら、別のリクエストでもキャッシュを読む。会話の冒頭には作業ディレクトリが入るので、実行ごとに一時ディレクトリを変える評価では、会話部分は共有されない（同じページの「Cache scope」）。
- SDK の assistant メッセージの `output_tokens` は仮の値: [Agent SDK のコストの資料](https://code.claude.com/docs/en/agent-sdk/cost-tracking#read-output-tokens-from-the-result-message)に明記されている。
- 読み取り専用のコマンドは自動で許可される: [permissions](https://code.claude.com/docs/en/permissions#read-only-commands)。`ls`、`cat`、`head`、`tail`、`grep`、`find`、`wc`、`diff`、`cd`、`git` の読み取り専用の形など。`Bash(x:*)` は `Bash(x *)` と同じ意味。
- 価格: Opus 5.5 と Haiku 5.5 は [価格のページ](https://platform.claude.com/docs/en/about-claude/pricing) と一致。Haiku 5.5 の 100K 超の割増は、キャッシュの読み書きにもかかり、プロンプトの長さはキャッシュの分も含めて数える。

食い違ったもの:

- Sonnet 5.5 のキャッシュの読み込みは、価格のページでは $0.10 / MTok（入力の 0.05 倍）。claude-api のスキルの価格の要約と、SDK に同梱の価格表は $0.20 だった。`eval/cost.ts` と `policy.ts` を $0.10 に直した。v1 の README の Sonnet のコストは SDK の見積もりなので、少し高めに出ている。

資料に記載がないもの（実測に従う）:

- `duration_api_ms` は、複数ターンの会話では累計で返る。
- トークンがあるかどうかで、読み込まれるツールとスキルが変わる。

対応:

- 評価の途中で TTL が変わらないよう、`CLAUDE_CODE_PROMPT_CACHE_TTL=1h` と `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=5m` を固定した（サブスクリプションの既定と同じ）。
- SDK のメッセージと突き合わせられなかったキャッシュの書き込みは、メインの会話なら1時間、サブエージェントなら5分として計算する。

追加で確かめたもの:

- `turn.step` で書き換えた effort は、実際に API に届いている。P1 の題材では、effort を下げたターンの出力が短すぎて差が見えなかったため、考える必要のある問題（`p1-think`、ツールなしの数え上げ）の2ターン目だけを low と max にして比べた（Haiku、各2回、`eval/results/2026-10-10T13-23-31-519Z.jsonl`）。
  - 2ターン目の出力トークンは low が 1,471 と 1,374、max が 2,586 と 3,882。所要時間は low が 6.9秒と 6.9秒、max が 11.8秒と 16.7秒。範囲は重ならない。
  - 切り替えた直後のリクエストは、ここでも直前のプロンプトを 100% キャッシュから読んだ。
  - 4回とも正解（215）。この問題は Haiku の low で足りる。

### P1. 段階表

- [x] モデルと effort の組の段階表を作る（例: Haiku/low、Haiku/medium、Sonnet/medium、Sonnet/high、Opus/medium、Opus/high）
  - 案（P3 の較正で見直す）:

    | 段 | モデル / effort | 使う場面 | 根拠 |

    | 1 | Haiku / low | 値や場所を答えるだけの質問、下調べ | effort の目安「low は小さな作業」 |
    | 2 | Haiku / medium | 小さな変更、サブエージェントの調査 | Haiku 5.5 の既定は medium |
    | 3 | Sonnet / medium | 範囲が明確な実装 | Sonnet 5.5 はエージェント的なコーディングを medium から始めるよう推奨。effort の目安「medium は範囲が明確な実装」 |
    | 4 | Sonnet / high | 検証が大事な不具合修正 | Sonnet 5.5 の既定は high。effort の目安「high は検証が大事な不具合修正」 |
    | 5 | Opus / medium | 計画、設計 | Opus 5.5 の既定は medium。`opusplan`（計画は Opus） |
    | 6 | Opus / high | 複雑な推論、失敗が続いたときの引き上げ先 | 「opus: complex reasoning tasks」 |
- [x] mod から、キャッシュを壊さずに会話の途中で effort を変えられるか確認する。できなければ「会話の中では effort を固定する」案と比べる
  - 手がかり: API には、メッセージ単位で effort を変えてもキャッシュを無効にしない beta（`mid-conversation-output-config-2026-07-01`、Opus/Sonnet/Haiku 5.5 で思考がオンのとき）がある。`turn.step` で effort を書き換えたときに Claude Code がこれを使うかは未確認。
  - 測り方: 実験用の mod [eval/schedule/](../eval/schedule/) で、決めたターン・ステップでモデルと effort を切り替え、切り替えた直後のリクエストが、同じモデルの直前のプロンプトをどれだけキャッシュから読んだかを見る（[eval/p1-cache.ts](../eval/p1-cache.ts)）。
    - 題材: 4ターンの会話 `p1-history`（1ターン目で src を全部読み、2〜4ターン目はツールなしで答える）。
    - 比較対象: `p1-fixed`（切り替えなし）、`p1-effort`（2ターン目で low、4ターン目で medium に戻す）、`p1-midturn`（1ターン目の途中のステップで low）、`p1-model`（2ターン目だけ Sonnet、3ターン目で Haiku に戻す）。いずれも Haiku が基本。
  - 結果（Haiku、各2回、2026-10-10、`eval/results/2026-10-10T13-05-29-194Z.jsonl`）:
    - effort の切り替えでは、キャッシュは壊れない。ターンの境目でも、ターンの途中のステップでも、切り替えた直後のリクエストが直前のプロンプトを 100% キャッシュから読んだ。書き込みは新しく増えた分だけ。
    - モデルの切り替えでは、切り替え先で会話全体を書き直す（約 19.5K。システムプロンプトとツール定義の分は、別の実行のキャッシュが残っていれば読める）。元のモデルに戻ると、そのキャッシュを 100% 再利用した。
    - 上位のモデルへの切り替えのコストは、ほぼ書き直しの分。1時間 TTL では書き込みが入力単価の2倍なので、Sonnet の1ターンが $0.081（Haiku だけの実行は $0.003）。
  - Sonnet と Opus でも同じだった（`p1-effort-sonnet`、`p1-effort-opus`。medium → 2ターン目で low → 4ターン目で medium。各2回、`eval/results/2026-10-10T13-10-30-119Z.jsonl`）。切り替えた直後のリクエストは、すべて直前のプロンプトを 100% 読んだ。
  - 結論: effort はターンごと（ターンの途中でも）に変えてよい。段階表の6段はそのまま使う。「会話の中では effort を固定する」案との比較は不要。
  - 冷えた状態と温まった状態の差は大きい。Opus の1回目は、システムプロンプトとツール定義のキャッシュがなく、約 15.5K を書いて $0.204、2回目は $0.110。比較対象の単独実行の値は、冷えた状態と温まった状態の両方で示す。
  - P4 への影響: 費用の面で効くのはモデルの切り替えだけ。上位のモデルへ上げると会話全体を書き直す（1時間 TTL で入力単価の2倍）ので、会話の大きさに比例して高くなる。元のモデルへ戻るのは、TTL 内なら安い。

### P2. 評価の題材

構成は「大きなシナリオ」と「少数の小さなタスク」の2本立てにする。

- [ ] **大きなシナリオを2〜3個作る**
  - 外部資料から要件、仕様、制約を読み取り、業務アプリケーションを設計・実装・テストし、最終の仕様書と報告書をまとめる。
  - 業務領域はシナリオごとに変える（1つの題材への過剰適合を防ぐ）。
  - 外部資料（架空の会社の議事録、規程、サンプルデータなど）は一式を作ってリポジトリに固定する。Web から取得すると内容が変わり、再現できないため。
- [ ] **シナリオの進め方を2通り用意する**
  - 複数ターンの台本: 作業の区切りごとに、ユーザー役が次の依頼を出す（要件をまとめて → 設計して → 実装して → テストして → 報告して）。短い続きの依頼も含める。
  - 1ターンの自律実行: 最初の依頼だけで最後まで進める。
- [ ] **採点方法を決める**
  - 実装: 資料から一意に決まる要件について、隠しの受け入れテストを用意する。
  - 設計書・仕様書・報告書: 採点基準を作り、どの比較対象の成果物かを伏せて Opus に採点させる。一部は人が抜き取りで確認する。
  - 作業の区切りごとに、採点できる中間地点を置く。
- [ ] **段階ごとの比較を用意する**: 前の段階の成果物を模範の版に固定してから、次の段階を始められるようにする。序盤のぶれが後に響くのを抑え、段階ごとにモデルを比べるため。通しの実行と併用する。
- [ ] **小さなタスクを作業の種類ごとに数問ずつ用意する**: 調査、小さな変更、実装、不具合修正、設計など。較正とルーターの判定精度の評価に使う。v1 の18問から使えるものは再利用する。
- [ ] 開発用と最終評価用に分ける（最終評価用には、ルーターの調整中は触らない）。
